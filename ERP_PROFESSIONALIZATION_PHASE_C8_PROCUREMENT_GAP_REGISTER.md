## Newly discovered this phase

### NF-C8-01 — RFQ list/detail had zero Workshop Isolation
- **Type**: SECURITY FINDING (same class as NF-01/Phase C6, much smaller scope).
- **Evidence**: `procurement_rfqs` has no `workshop_id` column of its own; only derivable via
  `procurement_requisitions.workshop_id`. Neither `procurementRfqList` nor `procurementRfqDetail`
  applied any such scoping.
- **Disposition**: **RESOLVED — Phase C8.** Both functions now join through the originating
  requisition's `workshop_id`, same convention used everywhere else in the file. Live-checked:
  no currently active user holding `procurement-rfq` is workshop-scoped (0 of 4 roles that hold
  it have an active, workshop-assigned user) — this was a latent, not actively-exploited, gap.
  Fixed anyway rather than left for a future user to discover.

### NF-C8-02 — Invoice list had zero Workshop Isolation
- **Type**: SECURITY FINDING (same class, same fix pattern).
- **Evidence**: `procurementInvoiceList` already joins to `procurement_purchase_orders` (which has
  `workshop_id`) but never used it for scoping.
- **Disposition**: **RESOLVED — Phase C8.** Same fix as NF-C8-01. No currently active user is
  workshop-scoped and holds `procurement-invoices` — latent, fixed anyway.

### NF-C8-03 — Un-cleaned QA residue from earlier, unlogged phases sitting in production data
- **Type**: DATA HYGIENE finding, not introduced by this phase.
- **Evidence**: Live query found 4 duplicated `_QA Supplier Ltd`/`_QA Phase2B Supplier` rows in
  `procurement_suppliers`, 8 `_QA Requisition`/`_QA Phase2B requisition` rows in
  `procurement_requisitions`, 4 `QA RFQ`/`QA Phase2B RFQ` rows in `procurement_rfqs`, and 6
  `QA-INV-*`/`_QA-P2B-INV-*` rows in `procurement_invoices` (with visible duplicate pairs,
  suggesting the same QA scenario was run more than once without cleanup between runs). This
  session's own memory of the Exception Management Phase 2/3 work describes "throwaway POs...
  all removed after" — the actual database shows the underlying supplier/requisition/RFQ/invoice
  fixtures from that work were never removed, only some of the PO-level test data was.
- **Why not fixed this phase**: this data was not created by Phase C8, and this session has an
  established precedent (see the "Stray QA test accounts" finding from an earlier, unrelated
  phase) of disclosing pre-existing stray QA data rather than unilaterally deleting it — the user
  may want to inspect it, and some of it may have downstream references (audit log entries,
  approval steps) that deserve a deliberate, reviewed cleanup rather than a rushed one bundled
  into an unrelated phase.
- **Disposition**: **OPEN — disclosed for the user's decision.** Recommended: a short, dedicated
  cleanup pass (delete the 4 suppliers, 8 requisitions, 4 RFQs, 6 invoices and their child rows,
  in FK-safe order) once confirmed safe to remove.

### NF-C8-04 — `procurement-dashboard` permission is far broader than the underlying list permissions
- **Type**: PERMISSION DESIGN observation, not a defect.
- **Evidence**: Live audit against `role_definitions` found 11 roles (`sales`, `finance`,
  `sawmill-leader`, `logistics`, `poles-leader`, `poles-supervisor`, `harvesting-leader`,
  `department-manager`, `vat-leader`, `sales-staff`, `operations`) hold `procurement-dashboard`
  but none of `procurement-orders`/`procurement-invoices`/`procurement-goods-receipt`/
  `procurement-suppliers`.
- **Disposition**: **Confirmed intentional, not fixed/changed.** This is a defensible "visibility
  summary for many roles, operational access for the procurement team only" design. This phase's
  own dashboard drill-down work (§18 in the Completion Report) was built to respect this exactly
  — each KPI tile is only made clickable for a viewer who actually holds the destination page's
  permission, rather than either (a) granting broader access (out of scope, needs the user's
  explicit go-ahead per this session's standing rule) or (b) wiring dead-end clicks for the
  majority of the dashboard's actual audience.

### NF-C8-05 — Minor concurrency response-semantics quirk (not a data-integrity defect)
- **Type**: MINOR UX/observability finding.
- **Evidence**: Two simultaneous, identical "approve" calls from the same actor both returned
  `{ok:true}` with the same `nextStage`, even though only one of them actually caused the stage
  transition (confirmed via direct inspection: exactly one approval-step row advanced, exactly
  one audit log entry was written — no corruption, no duplicate processing of business
  consequence).
- **Disposition**: **OPEN, low priority.** The core data-integrity guarantee holds; a future,
  small polish item could have the second concurrent caller's response distinguish "you decided
  this" from "this had already been decided," but this is not a correctness issue and was not
  fixed under this phase's own scope.
