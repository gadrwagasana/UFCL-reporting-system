1. Critical Issues

Issues that will cause total or severe failure in production. All were identified; the 3 URL bugs are already fixed in this session.
C-01 — Production APK API URL points to loopback-only port FIXED

Files: mobile/app.config.js:23, .github/workflows/mobile-release.yml (step 8 env block)

Problem: The production apiUrl in app.config.js defaulted to http://192.168.1.5:3001. The CI step 8 (Gradle build) did not set EXPO_PUBLIC_API_URL. In production the Express server binds to 127.0.0.1 (loopback) and port 3001 is blocked by UFW. Every API call from the production APK — login, harvest, deliveries, everything — would have failed with a network error.

Fix applied: (1) Updated app.config.js production default to https://192.168.1.5. (2) Added EXPO_PUBLIC_API_URL: https://192.168.1.5 to CI step 8 env block so the correct URL is baked into the APK at build time.

C-02 — OTA update checker uses blocked HTTP/port-3001 URL FIXED

File: mobile/src/services/updateChecker.ts:8

Problem: UPDATE_SERVER = 'http://192.168.1.5:3001'. The fetchLatestMeta() function catches any connection error and silently returns null. Since port 3001 is unreachable from LAN devices, every update check would silently fail. Devices would never learn about patches after v1.0.0.

Fix applied: Changed to 'https://192.168.1.5'. Nginx correctly proxies /version.json and /downloads/ through TLS on port 443.

C-03 — version-server.json apkUrl writes blocked URL into update metadata FIXED

File: .github/workflows/mobile-release.yml (step 11 line 139, step 13 line 245)

Problem: Two places in the CI workflow wrote http://192.168.1.5:3001/downloads/UFCL-production.apk as the apkUrl in the version metadata deployed to the company server. The mobile app reads this URL to download the patch APK — it would fail with connection refused.

Fix applied: Both occurrences changed to https://192.168.1.5/downloads/UFCL-production.apk.

Root cause for C-01, C-02, C-03: Development was done with Express bound to 0.0.0.0:3001 (accessible on LAN). The production nginx deployment was configured correctly in the server tools, but three source files were not updated to match. All three fixes are single-line text changes.

2. Major Issues

M-01 — Vehicle Fuel module is implemented but unreachable OPEN — awaiting decision

Files: mobile/src/navigation/LogisticsNavigator.tsx, mobile/src/navigation/types.ts

Problem: VehicleFuelStack.tsx and all three vehicle fuel screens were built in Sprint 5. The backend route POST /api/fuel/vehicle exists with requireRoles('logistics', 'admin'). However LogisticsTabParamList only defines DeliveryList and MyRequests — no VehicleFuel tab. The logistics role has no navigation path to these screens.

Impact: Logistics staff cannot log vehicle fuel at all. The User Manual describes Vehicle Fuel under the Logistics section, which is inaccurate for v1.0.

Options (user decision required):

  • Option A — Add to v1.0: Wire VehicleFuelStack into LogisticsNavigator as a third tab. Three-line change; backend already supports it.
  • Option B — Defer to v1.1: Mark Vehicle Fuel as "coming in v1.1" in the User Manual. Update Release Notes accordingly.

3. Minor Issues

Min-01 — LoginScreen version string shows "v1.0" instead of "v1.0.0" FIXED

File: mobile/src/screens/auth/LoginScreen.tsx:110

Updated to "UFCL Mobile v1.0.0" to be consistent with the release tag and all documentation.

Min-02 — Mechanic role has no Profile tab COSMETIC

File: mobile/src/navigation/MechanicianNavigator.tsx

MechanicianTabParamList has MachineLogList, MachineFuelList, MyRequests but no Profile tab. Users in the mechanician role cannot view or update their profile. All other role navigators include Profile. Suggest adding for v1.1.

Min-03 — TODAY_FMT computed at module load time in HarvestListScreen COSMETIC

File: mobile/src/screens/harvest/HarvestListScreen.tsx

const TODAY_FMT = format(new Date(), 'dd/MM/yyyy') is evaluated once when the module loads. If the app stays open past midnight, the "today" date highlight won't update until the app is restarted. Purely cosmetic; no data is affected.

Min-04 — CasualLabourRequest.labour_items has union type string | string[] TYPE SAFETY

File: mobile/src/types/api.ts

The labour_items field is typed as string | string[]. If the API consistently returns an array, the string variant is unnecessary. If a string is ever returned and UI code iterates it as an array, a runtime crash would follow. Should be pinned to whichever type the backend actually returns.

Min-05 — err: any anti-pattern in create screens CODE QUALITY

Several *CreateScreen.tsx files use catch (err: any). Using catch (err: unknown) with a type narrowing guard is safer. Not a runtime risk but degrades TypeScript's ability to catch type errors. Defer to v1.1.
